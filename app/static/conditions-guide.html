00数据管线总览

所有条件都走同一条链路。理解这张图，下面 37 个条件就只是"取哪个字段、怎么算"的差异。

数据源 计算/转换 字段值 比较判断

统一求值入口是 _eval_cond（rule_engine.py:228-259）：把条件类型经 COND_FIELDS 映射成字段名，从 fields 取值，用 OPS 表比较阈值；logic=="非" 时对该项取反。组内全部条件 AND，组间按 或/且/非 顺序链条折叠（rule_engine.py:262-293）。

三类"无数据"兜底约定（防误报核心）

① 延迟类（血糖/泵/手表离线）无数据 → 9999，让"大于N"必然成立、"小于N"不成立。
② 大剂量距今天数无记录 → 0（视为刚打过），"大于N分钟"不触发。
③ 充电/掉电历史类（_STRICT_FIELDS）历史不足 → None，_eval_cond 直接判"数据不足"不满足（rule_engine.py:248-249），重启后需积累约 N+30 分钟才生效。

血糖历史缓冲→ 反向数连续 >180→ BG_HI_DUR→ >= 60 ?

示例："高血糖已 1 小时才提醒" = 大于等于 60。内部 mg/dL 口径，与显示单位无关；当前已回落则归 0。

连续低血糖时长(分钟)→ bg_low_dur历史类
派生：血糖连续低于 3.9 mmol/L（70 mg/dL）的分钟数，固定临床阈值
血糖历史缓冲→ 反向数连续 <70→ BG_LO_DUR→ >= 15 ?

示例："低血糖持续 15 分钟才报"——过滤一闪而过的假性低值。重启后需积累数据才生效。

def _dur_at(hist, want):
    if hist[-1].chg != want: return 0     # 当前不满足=0
    start = 最新ts
    for p in reversed(hist):
        if p.chg != want: break
        start = p.ts
    return (最新ts - start)/60000

接触不良判定用：连续充电≥30 但仍在掉电 = 稳定插着却充不进。

08求值机制：组内 AND + 组间链条

组内条件全部 与 才 cond_ok；非 组取反后是 AND NOT 排除语义（只排除、不贡献命中），hit_names 收集 eff 为真的组名供选组与 {组名} 模板。

09路线图：还在考虑的方向

以下方向数据链路较复杂或有歧义，暂未实现，供后续版本评估。

按设备名区分手表/手机数据 需设备识别策略

手机+手表同时向同一 Nightscout 上传时，"手表电量"取的是最新一条 devicestatus，可能读到手机。需按 uploader 设备名过滤，涉及多品牌命名差异。

COB 消耗偏差 / 基础率偏离计划 需配置基线

"实际 COB 与预测偏差过大""当前基础率偏离用户设定基线"需要先导入泵的基础率表作为基线，配置成本较高。

夜间低血糖预测提前量 需预测外推

基于 minGuardBG 斜率外推"预计 40 分钟后跌破 3.9"，比"最终预测BG 小于 3.9"更早预警；需要更长的历史缓冲与防抖设计。

小结

37 个条件已覆盖血糖/增量/趋势、IOB/COB/预测、大剂量/碳水、手表/充电历史、泵、时间六大维度，"无数据兜底"与"历史类防误报"贯穿全部。上次大剂量已排除 SMB 自动微剂量，只认手动大剂量。历史类条件（掉电幅度、充电状态·N分钟前、连续时长、波动幅度、连续高/低血糖时长）重启后需积累约 N+30 分钟数据才生效，期间一律判不满足。
